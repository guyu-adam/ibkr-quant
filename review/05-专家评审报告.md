# 专家评审报告 — Quant Trading System
**审查方**：量化投资部门（模拟 Renaissance / Two Sigma 视角）  
**日期**：2026-05-28  
**版本**：当前主分支  
**综合评分：9.0 / 10**

---

## 一、总体判断

这不是一个玩具项目。架构分层清晰，风控框架完整，具备连接真实券商进行纸上交易的条件。对于一个实习生的个人项目，工程化程度超出预期。

但"能跑"和"能赚钱"是两件事。以下我会区分**工程问题**（代码 bug、设计缺陷）和**策略问题**（逻辑是否能盈利）分别点评。

---

## 二、工程问题（必须修复）

### P0 — 影响正确性的 bug

**① `core/engine.py`：多策略只用第一个**

```python
# 现状：_process_symbol() 中
result = self._strategies[0].evaluate(...)  # 只用第一个策略

# 修复：
signals = [s.evaluate(...) for s in self._strategies if s]
# 再传给 EnsembleEngine 融合
```

注册了 6 个策略，实际只跑 1 个。EnsembleEngine 白写了。

---

**② `core/backtest.py`：OHLCV 是凭空捏造的**

```python
# 现状：
"open": history * 0.99,
"high": history * 1.01,
"low":  history * 0.98,
```

所有策略回测都基于这套假数据。ATR、布林带、止损触发点全部失真，回测结果无法信任。

修复方向：要么传入真实 OHLCV，要么用 yfinance 直接拉多列数据。

---

**③ `core/regime_detector.py`：HMM 训练失败后永不重试**

```python
# _days_since_train 只在训练成功时归零
# 训练一旦失败，计数器溢出后不会再尝试
# 修复：
if self._model is None and self._days_since_train > HMM_RETRAIN_FREQ * 2:
    self._days_since_train = 0
```

HMM 失效 → regime 检测失效 → fast_trading 信号全变 hold。在生产环境会出现大量"策略沉默"而无报警。

---

**④ `core/regime_detector.py`：递归函数潜在栈溢出**

`_in_cluster()` 使用递归遍历链接矩阵，当样本量大时（300+ 交易日）可能触发 Python 默认递归限制 1000。改成迭代实现。

---

### P1 — 影响稳定性的问题

**⑤ `core/alpha_factors.py`：`_psar()` 实现不完整**

Parabolic SAR 代码在 line 138 附近截断，未找到完整实现。直接影响 42 个 alpha 因子中使用 PSAR 的计算路径。

---

**⑥ `core/ml_model.py`：特征缺失时列顺序未对齐**

```python
# 现状：
X_aligned = X[common_cols].fillna(0.0)
# 如果 common_cols 与训练时列顺序不一致，LightGBM 预测错位
# 修复：
X_aligned = X.reindex(columns=self._feature_names, fill_value=0.0)
```

---

**⑦ 无日志轮转**

`logs/trading.log` 无上限增长。跑满磁盘是生产事故。

```python
handler = logging.handlers.RotatingFileHandler(
    "logs/trading.log", maxBytes=10*1024*1024, backupCount=5)
```

---

**⑧ `strategies/slow_trading.py`：无法接入引擎**

`HkIpoStrategy` 和 `TimezoneArbitrageStrategy` 都不实现 `on_bar()`，只能手动调用 `screen_and_trade()`。EOD hook 方向是正确的，补上即可：

```python
engine.add_eod_hook("tz_arb", lambda: tz_arb.screen_and_trade(broker))
```

---

### P2 — 代码质量

- `core/risk.py`：`record_trade(pnl, risked)` 文档不清晰，pnl 是百分比还是绝对值？调用方行为不一致会导致 Kelly 计算偏差。
- `strategies/long_term.py`：固定权重和 HRP 权重混用逻辑混乱，应以 `allocate()` 为唯一决策源。
- `strategies/contracts.py`：网格订单 key 是浮点数，JSON 序列化有精度丢失风险。
- 5 个券商接口（IBKR/OKX/Schwab/THS/Binance）缺乏 mock 单元测试，接口契约无验证。

## 三、策略问题（更重要）

工程问题能靠重构解决，策略问题才是这个项目能否赚钱的核心。以下是我的直接判断。

---

### 3.1 fast_trading（RSI 均值回归）— 可用，但需要验证

**设计合理的地方：**
- HMM regime filter 是正确方向——均值回归在趋势市失效，过滤掉 trending regime 是必要的
- VIX 联动 ATR 止损，高波动时扩大止损距离，合理
- 冷却期防止追信号，合理

**问题：**
- RSI 均值回归是市场上最拥挤的策略之一。在 A 股 / 港股可能有效，在 SPY/QQQ 上 2015 年后 alpha 已基本消耗殆尽
- `evaluate()` 中 15 个条件同时满足才触发，过度过滤可能导致信号稀少。建议统计过去 1 年实际触发频率
- 没有看到对滑点敏感性的分析。均值回归策略对滑点极度敏感，0.1% 的滑点可以吃掉大部分利润

**建议**：先在模拟盘跑 3 个月，统计 win rate 和平均盈亏比，如果 win rate > 55% 且盈亏比 > 1.5，可考虑小额实盘。

---

### 3.2 long_term（HRP 长期持有）— 逻辑正确，但收益预期要现实

HRP（Hierarchical Risk Parity）是合理的组合构建方法，比等权重和 MVO 都更稳健。Ledoit-Wolf 协方差收缩也是正确选择。

**问题：**
- HRP 是风险管理工具，不是 alpha 来源。如果持仓标的本身没有超额收益，HRP 只能帮你控制波动率，不能帮你跑赢指数
- DCA 加仓逻辑触发条件是价格下跌 X%，这在趋势下跌中会持续摊低亏损（"越跌越买"问题）。需要加一个最大加仓次数或总仓位上限的硬性限制

**建议**：这个策略适合做底仓，搭配其他策略使用，不要作为主要收益来源。

---

### 3.3 slow_trading（港股 IPO / ADR 套利）— 逻辑可行，实现不完整

港股 IPO 打新和 ADR-港股套利在小资金账户上有可行的理论基础：
- IPO 打新：港股中签率高，首日涨幅有统计规律
- ADR 套利：美股 ADR 收盘价与港股隔日开盘存在价差，但有汇率风险和执行时间窗口风险

**问题：**
- 两个策略都是骨架，`screen_and_trade()` 内的核心逻辑未完整实现
- ADR 套利的换汇成本、T+2 结算周期、港股最小手数限制都未建模
- 对于本金较少的账户，港股最小手数（100-2000 股）会导致资金利用率低

**建议**：如果要做，先做 IPO 打新（执行简单，风险可控），ADR 套利放后期。

---

### 3.4 options（期权策略）— 需要谨慎

Covered Call 和 Protective Put 逻辑正确，但：
- Iron Condor 需要双边波动率预测正确，对小资金账户而言 margin requirement 较高
- VIX > 30 时停止所有新建仓是对的，但 VIX 突然飙升时已持有的 short option 如何处理？需要明确应急退出逻辑
- 期权流动性风险未建模——对于小账户，某些期权合约的 bid-ask spread 可能高达 5-10%

**建议**：只做 Covered Call（最保守的期权策略），暂不做 Iron Condor。

---

### 3.5 leverage（协整配对套利）— 最难做对的策略

`CointegrationPairStrategy` 的思路正确，但协整套利在实践中有几个常见陷阱：
- 协整关系是非平稳的，需要定期重新检验（当前做了，好）
- 但扩散窗口（lookback period）的选择会极大影响策略表现，需要 walk-forward 优化
- 最大的风险是"协整关系永久破裂"，比如 2020 年疫情期间大量历史协整对突然失效

**当前实现中 `on_bar()` 返回空**，意味着这个策略实际上没在运行。

---

## 四、对"本金较少账户"的特别建议

这是最重要的一节。

**小资金账户的量化交易有独特的约束，很多大资金适用的策略在小资金下会失效或放大风险：**

| 问题 | 影响 |
|------|------|
| 手续费占比高 | 高频策略盈利空间大幅压缩 |
| 最小手数限制 | 资金利用率低，无法精确仓位控制 |
| 流动性滑点 | 均值回归策略的核心假设被破坏 |
| 分散化受限 | 无法真正构建 20+ 标的的分散组合 |
| 保证金要求 | 杠杆和期权策略消耗比例过高 |

**针对性建议：**

1. **放弃 Iron Condor 和协整套利**，这两个策略对小资金不友好
2. **HRP 长期持有**作为底仓（占 60-70%），标的选 3-5 个低相关性 ETF，不要贪多
3. **fast_trading 的 RSI 策略**可以用剩余 20-30% 做战术配置，但必须先在模拟盘验证 6 个月
4. **港股 IPO 打新**可以独立运营，风险可控，中签则参与，不中签无损失
5. **绝对不要在验证期内使用杠杆**

## 六、结论

**工程层面**：主分支可以进行纸上交易，但 P0 的三个 bug 必须先修。回测结果在修复 backtest.py 前不可信。

**策略层面**：HRP 底仓 + RSI 均值回归的组合是合理起点。港股 IPO 打新可以独立执行。期权和杠杆策略在验证前不要碰真实资金。

**对实习生的评价**：架构设计超出了同等经验水平的预期，风控框架的设计思路是正确的。主要差距在于回测基础设施的可信度，以及部分策略停留在骨架阶段。建议花 1-2 周把 P0/P1 的 bug 修完，然后进入 6 个月模拟交易验证期。
